# oir —— 订单截图识别（Order Image Recognition）

这个包只做一件事：**把一张电商订单截图（淘宝 / 天猫 / 京东 / 拼多多 / 抖音）变成一份订单列表**，
交给调用方填进"从订单建单并入库"的核对表。它**不写库**，也不改库存——入库是
`MfgReceiptEvents` / `MfgReceiptEvents.ordersJson` 的事。

拆出来的目的：让第三方可以**只看这一个包**就理解算法、指出更好的做法，不必先读懂 1.4 万行的
`MfgServices`。对外入口仍是 `org.langhua.ofbiz.mfg.MfgOrderScan`（控制器的 java event 指向它），
它只是把两个请求转发到这里。

包里有三个文件：

| 文件 | 做什么 | 依赖 |
| --- | --- | --- |
| `OirScan.java` | 联网、分段、提示词、重试、打分 | HTTP + AWT（读图）+ `MfgServices.setting` |
| `OirOrders.java` | **纯函数**：读答案 → 订单列表 → 合并 → 整理 → 金额核对 | 只有 `java.util` + 零件号规范化（`MfgServices.fittingComponentCode` 等） |
| `README.md` | 本文件 | — |

**要审计算法，只看 `OirOrders`（2167 行）就够了**；`OirScan` 那 1388 行是"怎么问、怎么切、怎么重试"。

## 1. 处理流程

```
上传 multipart(image)
  ├─ 图片大小/格式校验（MAX_IMAGE_BYTES，超长图不缩：会分段识别）
  ├─ 读图 → 分段（自适应段高，见 §2）
  ├─ 每段并发调用视觉服务（最多 MAX_PARALLEL=4 段同时）
  │    ├─ 提示词：PROMPT / SHORT_PROMPT（段一律用短的）
  │    ├─ 失败重试：SLICE_ATTEMPTS=3 次，按 answerScore 保留最好的一次
  │    └─ 触发重试的信号：空答案、答案像模板、数量/金额读不出、rowCount 与行数不符、
  │       每行都是 1 件但页面印了包量、两块明细完全相同、(整图时)实付与明细对不上
  ├─ 解析：orderListFrom(reply) → itemsIn() → 每单 {orderNo, shop, platform, orderDate,
  │        paidTotal, freight, discount, refunded, closed, rowCount, lines}
  ├─ 合并：OirOrders.mergeOrders(answers, blocksSaid)（见 §3）
  ├─ 整理：OirOrders.tidyOrder(order)（见 §4）
  └─ 核对：OirOrders.checkOrderTotals / rowsMissing → 给每行写 note（页面上标"请核对"）
```

返回结构是固定的，调用方按它渲染核对表：

```json
{"ok":true,"message":"识别到 23 张单，核对后点「导入这些单」","count":23,
 "orders":[{"orderNo":"...","shop":"...","paidTotal":"14.00","lines":"code\tname\tqty\tamount\n...", "note":"..."}]}
```

## 2. 分段：段高是量出来的，不是常数

一张 3000×16000 的"我的订单"整页，一次丢给模型会整块漏读（实测 3 次里只有 1 次数对），
所以要切段。两件事分开看：

| 环节 | 做法 | 依据 |
| --- | --- | --- |
| **切点位置** | 在"目标高度附近"找**两个橙色按钮之间最宽的空白段**，取中点 | 一页每块印 2~3 个橙色按钮（加入购物车 / 申请售后 / 再买一单），窄缝在块内、宽缝才是块与块之间 || **段高** | `blockHeightOf(image)`：把整页按行读成"暗度曲线"，与自身做自相关，**重复最好的间距 = 一块的高度**；段高 = 2 × 块高，clamp 到 [600, 2000] | 一页订单块形状重复（标题行 / 图片 / 标题 / 价格），实测 689 行，与 16384/23 ≈ 712 差 3% |

量不出来（纯白 / 纯黑 / 页面没有重复）时回落到 `SLICE_HEIGHT = 900`。
相邻段共享 `SLICE_OVERLAP = 500` 行，被切到的那一块在下一段里仍然完整。

**实测（同一张 3255×16384、23 单的图，每次 10 连测）**

| 方案 | 结果 |
| --- | --- |
| 固定 2400 行/段 | 1/3 正确，且会整块丢失 2~3 张 |
| 固定 900 行/段 | 9/10 正确 |
| 自适应（689→1378 行/段，12 段） | **10/10 正确，无重复单号** |

## 3. 合并：同一块被读了两次怎么办

`mergeOrders` 的输入是"每段的答案"，输出是整页的订单。要点：

1. **同一个订单号 = 同一单**：行拼接，缺失字段互补；号长按整页众数校正（读多/读少一位时）。
2. **两个对象都是同一块**（模型把一块答成两条）：
   - 实付**相同** → 并回一张（一页只印一个实付款）；
   - 其中一条**完全没有金额**（`paidTotal=0.00`、店铺空）→ 视为同一块的片段；
   - 一条的金额恰是另一条 **单价 × 数量** → 小的那条是单价，丢掉。
3. **两条不同块被读成同一个号**：实付**不同**时才拆开留着（宁可多一行让人删，也不吞单）。
4. 跨段：同号且同实付 → 合并；同号不同实付 → 拆开。

相关规则函数：`OirOrders.mergeOrders / numbersOfTheSameOrder / onePrintsThePriceOfTheOther`…（都在本包 `OirOrders` 里，不再跨包）。

## 4. 整理：让每一单的"明细合计 = 实付 + 优惠 − 运费"

`OirOrders.tidyOrder` 依次尝试（只用**能对上钱**的那种读法）：

| 场景 | 规则 |
| --- | --- |
| 一包单价被当成整行金额 | `moneyOfOnePack`：缺口正好是某行金额 ×(包数−1) 时，那一行改成 `单价 × 包数`（要求恰好一行能解释） |
| 把"实付款"当成一行明细 | `withoutTheRowThatIsThePaidTotal`：≥3 行且只有一行等于整单实付时删掉它 |
| 单价被当成行金额 | `readingThatAddsUp`：允许 ×数量 |
| 重叠段读到的重复行 | `withoutRepeatedRows`：只在明细合计大于实付时删，删到对得上为止 |
| 页面底部"猜你喜欢"被算进最后一单 | `withoutTheTailThatDoesNotFit` |
| 实付含运费被算两遍 | `goodsWithoutFreight` |
| 整块只有一行 | 该行金额 = 实付 − 运费 |

金额核对容差 `roundingSlack = 0.005 × 件数 + 0.005`（页面把单价四舍五入到分）。常量名 `HALF_A_FEN`，
两份读数之间的容差是 `MONEY_TOLERANCE = 0.06`（六分），都带来源说明放在 `OirOrders` 顶部。

## 5. 已知失败模式（都是实测到的，不是猜想）

| 现象 | 现在的处理 |
| --- | --- |
| 模型整块漏读（21 张） | 段切小后基本消失；整页仍少时页面会提示"截图上看上去有 N 张，这次只读出 M 张" |
| **模型凭空多编一张单（+1 行）** | 目前**不能自动识别**，只带 note 让人核对（详见 §6 问题 1 的实测数据）。 |
| 19 位订单号少一位 / 相邻两位写反 | 用"整页号长众数 + 同实付 + 一条子序列"规则并回；仍可能读错，属已知局限 |
| 一块印 4 行、模型只读出 2 行 | `rowCount` 与行数比对后提示"截图印了 4 行明细，这次只读出 2 行" |

## 6. 请审计的问题（欢迎直接改）

1. **块边界检测**：现在靠"橙色按钮 + 最宽缝"。有没有更稳的信号（页面分隔线、图片色块的周期、频域峰值）？
   **实测过了（2026-10-27，3434×16384、23 单的真实页）**：
   - 旧规则（一行里橙色总量 ≥ 宽度的 4%）得到 **32** 个锚点：23 个是真正的「再买一单」按钮，另 9 个是
     橙色**文字行**——表头的 `订单详情 >` / `交易成功` 一行就能凑出 200 px 橙色，券条同理；
   - 换成「**最长一段连续橙色** ≥ 宽度的 4%」后是 **25** 个：23 个块按钮 + 页头那个按钮（y≈118，x≈2533）
     + 页面底部推荐区的按钮（y≈13276，x≈1666）。块按钮彼此 x≈2431~2448、带宽 187~204 px，与那两个明显不同。
   - 所以「数按钮」**只差去掉页头/页尾两个**（它们的 x 与其它 23 个差 > 60 px）。这一步还没做：一旦数准，
     就能在 `scan` 里把"读出的单数"与"图上的块数"对上，从而自动发现"模型凭空多编的一张"（§5 第二行）。
   - 「最长连续橙色」这一条**已经改进代码**（`blockAnchors`），切点也随之变了（12 段不变，个别切点移动
     几百行），同一张图 10 连测仍是 **10/10 都是 23 张 / 23 个不重复号**，与改之前持平。
     量这个的工具放在 `tools/oir-anchors/`（`AnchorAudit` 打印锚点与切点，`LongestOrange` 打印每段的带宽）。
2. **段高估计**：自相关取全局最大值。是否该用"多个候选峰值 × 段内块数一致性"来选？换平台/换缩放是否稳？
3. **合并规则**：现在是一串 if。能否换成一个**全局最优化**（把每段读法当作候选块，用费用函数做序列对齐 /
   匈牙利匹配），从而一次处理"漏读、重读、串号、串行"？
4. **多次采样 + 投票**：同一段读 2~3 次，按"单号 + 实付 + 明细"投票，是否比现在"重试 + 打分保留最好"更稳？
5. **提示词**：能不能换成更"窄"的输出格式（例如每单一行、字段用固定分隔符），让模型少犯格式错误？
6. **金额核对**：淘宝/天猫/拼多多/抖音里还有哪些写法（满减、店铺券、跨店优惠、"实付含运费"）没覆盖？

## 8. 约束（改的时候别破坏）

- **不能写库**：这个包只返回订单列表；入库、幂等（订单号为键）、退款黑名单都在调用方。
- **返回结构不能变**：`{"ok","message","count","orders":[{...}]}`，页面的核对表按它渲染。
- **`MfgOrderScan` 这个类名不能删**：`controller.xml` 的 `<request-map uri="orderImage">` 指向它。
- 判定阈值（容差、包数上限、段高上下限）都在类顶部，改了请同步本文件 §2 §4 的说明与 `AGENTS.md`。

## 9. 外部审计意见的处理（2026-10-27）

第三方按「代码结构 / 算法稳健性 / 性能 / 可测试性 / 细节」提了十五条，结论如下。

**已改（行为不变，161 个单测 + 真实图片 23 张 / 12 段重跑一致）**

| 意见 | 做法 |
| --- | --- |
| 魔法数字散落 | `OirOrders` 顶部集中为 `MONEY_TOLERANCE` / `HALF_A_FEN` / `PRACTICALLY_ZERO` / `MAX_PACKS` / `MISSING_DIGITS_ALLOWED`，注释写明来源与实测依据 |
| 正则每次重编译 | `TRADE_NOTE` / `PACK_SUFFIX` / `BLANKS` 改成 `static final Pattern`（`bareCode` / `rowKey` 用） |
| `anonymousOk` 含义模糊 | 参数改名 `partial`，与 `OirScan` 里那个切片标志同名 |
| 线程池未优雅关闭 | `shutdownNow()` + `awaitTermination(5s)` 放进 `finally`（超时的切片会被取消，不留线程和图片） |
| 重试固定间隔 | `pause(attempt)` 指数退避 700 / 1400 / 2800 ms |
| 日志不够详细 | 每次重发记 `Attempt N of M scored X (kept Y, best Z), asking again: <原因>`，原因由 `whyAskAgain()` 给出 |
| 悬空 javadoc | `orderListFrom(String)` 上面那段（`nameWithFullCode` 的）是搬迁留下的，已换成正确说明 |

**没改（附理由，欢迎再挑战）**

| 意见 | 为什么不改 |
| --- | --- |
| 容差收紧成 `max(0.01×件数, 0.05)` | `0.005×件数` 不是拍脑袋：页面把单价印到分，100 件 × 单价误差 0.005 = 0.5 元。收紧会让 Step 129 修掉的「请核对」噪声回来（27 张单从 7 条降到 0 条），那些差额都是页面四舍五入，不是漏读 |
| 金额换 `BigDecimal` | 钱只在 `round2(...)`（两位）之后比较，误差来自**页面四舍五入**而不是二进制浮点；换 BigDecimal 要改每一处规则，且不改任何一次判定结果 |
| `refunded` / `closed` 改枚举 | 这两个字段是给页面、`ordersJson`、`MfgRefundedOrder` 的**线格式**（字符串），枚举只会在边界反复转换 |
| 块高多信号融合 | 切点是靠按钮缝定的（§2），块高只决定「一段放几块」；实测 12 段、10 连测 23/23，动它是拿已验证的结果赌未验证的收益。审计问题 2 仍然开放 |
| `VisionClient` 接口注入 | `askVision` 已 `public static` 且只做一次 HTTP；端到端已有 `mock-vision.ps1` 假接口。抽接口会把静态工具类改成需要注入状态的对象 |
| `tidyOrder` 拆小方法 | 这十几步的**顺序本身就是规则**（Step 129：`goodsWithoutFreight` 必须在丢汇总行之前）。拆进独立方法会让这个约束藏起来，而它正是出过错的地方；每步已有注释 |
| 切片先 PNG 再 JPEG | 切片的大小主要来自商品图，PNG 重压收益很小；JPEG 只在 >4 MB 时走，实物小字实测可读 |
