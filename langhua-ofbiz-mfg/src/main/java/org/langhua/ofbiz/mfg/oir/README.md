# oir —— 订单截图识别（Order Image Recognition）

这个包只做一件事：**把一张淘宝 / 天猫订单截图变成一份订单列表**，
交给调用方填进"从订单建单并入库"的核对表。它**不写库**，也不改库存——入库是
`MfgReceiptEvents` / `MfgReceiptEvents.ordersJson` 的事。

拆出来的目的：让第三方可以**只看这一个包**就理解算法、指出更好的做法，不必先读懂 1.4 万行的
`MfgServices`。对外入口仍是 `org.langhua.ofbiz.mfg.MfgOrderScan`（控制器的 java event 指向它），
它只是把两个请求转发到这里。

包里有三个文件：

| 文件 | 做什么 | 依赖 |
| --- | --- | --- |
| `OirScan.java` | 联网、分段、提示词、重试、打分 | HTTP + AWT（读图）+ `MfgServices.setting` |
| `OirOrders.java` | **纯函数**：读答案 → 订单列表 → 合并 → 整理 → 金额核对 | 只有 `java.util` + 零件号规范化（`MfgServices.fittingComponentCode` 等） |
| `README.md` | 本文件 | — |

**要审计算法，只看 `OirOrders`（2167 行）就够了**；`OirScan` 那 1388 行是"怎么问、怎么切、怎么重试"。

## 1. 处理流程

```
上传 multipart(image)
  ├─ 图片大小/格式校验（MAX_IMAGE_BYTES，超长图不缩：会分段识别）
  ├─ 读图 → 分段（自适应段高，见 §2；先裁掉左右空白：`contentColumns`）
  ├─ 每段并发调用视觉服务（最多 MAX_PARALLEL=6 段同时）
  │    ├─ 提示词：PROMPT / SHORT_PROMPT（段一律用短的）
  │    ├─ 失败重试：SLICE_ATTEMPTS=3 次，按 answerScore 保留最好的一次
  │    └─ 触发重试的信号：空答案、答案像模板、数量/金额读不出、rowCount 与行数不符、
  │       每行都是 1 件但页面印了包量、两块明细完全相同、这一段印着几个块却答得更少、
  │       (整图时)实付与明细对不上
  ├─ **单号再读一次**：同一段裁成左侧 1700 宽的一条（`STRIP_WIDTH`），只问
  │       订单号 / 下单日期 / 店铺（`HEADER_PROMPT`）；两次读数**不按大小定输赢**，
  │       合并后由 `settleNumbers` 用“这一页印单号的位数”判定（见 §3 第 6 条）
  ├─ 解析：orderListFrom(reply) → itemsIn() → 每单 {orderNo, shop, platform, orderDate,
  │        paidTotal, freight, discount, refunded, closed, rowCount, lines}
  ├─ 合并：OirOrders.mergeOrders(answers, blocksSaid)（见 §3）
  ├─ 对账：blockCountOf(image) 数出图上有几个块，`foldExtraReads` 把同号两行折回一张（见 §3 第 5 条）
  ├─ 整理：OirOrders.tidyOrder(order)（见 §4）
  └─ 核对：OirOrders.checkOrderTotals / rowsMissing → 给每行写 note（页面上标"请核对"）
```

返回结构是固定的，调用方按它渲染核对表：

```json
{"ok":true,"message":"识别到 23 张单，核对后点「导入这些单」","count":23,
 "orders":[{"orderNo":"...","shop":"...","paidTotal":"14.00","lines":"code\tname\tqty\tamount\n...", "note":"..."}]}
```

## 2. 分段：段高是量出来的，不是常数

一张 3000×16000 的"我的订单"整页，一次丢给模型会整块漏读（实测 3 次里只有 1 次数对），
所以要切段。两件事分开看：

| 环节 | 做法 | 依据 |
| --- | --- | --- |
| **切点位置** | **一个块一段**：切在块自己的表头上（`button - BUTTON_TO_HEADER`） | 一块一个按钮，所以「两个按钮之间」就是**一个块本身**；旧做法取这段的中点，等于每次都切在块的中间（Step 159） |
| **段高** | 没有目标高度了：块多高，段就多高（`blockHeightOf` 只剩“量不出来时回落到 900”这一条退路） | 一张 14 单的页面上块高 300～2700 行，任何固定高度都会切开某个块 |

量不出来（纯白 / 纯黑 / 页面没有重复）时回落到 `SLICE_HEIGHT = 900`。
**切在表头上的段不需要重叠**（一块永远完整地在某一段里）；只有「找不到按钮、退回去按空白行切」那条路
才继续用 `SLICE_OVERLAP = 500`。

**块高可以差很多，所以没有目标段高**：一张 14 单的页面上块高从 300 到 2700 行不等（其中一块印了十三行电阻，
2769 行）。一个块一段以后，**比一般块高一倍的块也只是一个大一点的段**：实测那段 2769 行、单独一次调用，
把那一单的十三行一次看全。旧做法按“目标高度”在这段上切了两刀，每半只读出几行，两半的钱都既不是实付也不是别的什么。
代价是调用数等于块数（14 单 = 14 次，加 14 次只问单号的带子），6 路并行下仍只要二三十秒。

**页面底部不是订单**：最后一个块以它的按钮结束，再往下是「猜你喜欢」信息流（有价格、有自己的按钮，
却没有一张订单）。实测那张 23 单的图，信息流占了底下 **4700 行**——以前这里花了 3 段（12 段里的 25%），
还可能让模型凭空编一张单。

**切在哪里由页面自己说**（`tailCutOf`，Step 161）：一单内两行商品之间空 30~80 行（实测 56~78），
列表与「猜你喜欢」之间空 500 行以上；所以截点是**第一条既 ≥ `MIN_TAIL_GAP`（300）又 ≥ 2× 列表内部最宽空白带**的空白行。
图 13 的截点因此是 13130 而不是 10372——**旧规则按块高截，而块高是“页面重复的那些块”测出来的平均值，
最后一单可以比它高好几倍**（那一单 10 行、块高 3130）：10372 以下全被切掉，模型就照着实付 20.00 补出 10 行，
有时补对、有时只补 1~2 行，钱还对得上，页面一声不响（Step 161）。
信息流的卡片**带图**时没有这么宽的空白带（实测 18~40 行），这时退回「最大的一块」：
`max(300, blockHeight, 页面上最宽的两按钮间距)`，**永远 ≥ 旧截法**，所以不会比以前切得更早；
没有按钮的图（非订单截图）整张保留。

**实测 15 张历史截图**：新截点全部 ≥ 旧截点（13 张更大或整张保留），单数不变。

**每段还多一道核对**：`blocksInside` 数出“这一段完整显示几个块”（上一个按钮已进段、本块的按钮也在段内），
一段印 2 个块只答 1 个就重发这一段（`whyAskAgain`）。整段丢掉一块时其他检查都看不出来：金额自己是对得上的。

**实测（同一张 3255×16384、23 单的图，每次 10 连测）**

| 方案 | 结果 |
| --- | --- |
| 固定 2400 行/段 | 1/3 正确，且会整块丢失 2~3 张 |
| 固定 900 行/段 | 9/10 正确 |
| 自适应（689→1378 行/段，12 段） | **10/10 正确，无重复单号** |
| 同上 + 截掉底部信息流（9 段，6 并行） | 20 连测：19 次 23 张、1 次 24 张（那一行是模型编的新单号），单次约 12 秒 |
| 同上 + 裁白边 + 单号读两遍（按位数判定） | **50 连测：47 次 23 张全对（94%）**，无单号位数错误；3 次 24 张（编了个新号），单次约 13 秒 |
| 同上 + “一模一样”提示只在多出一行时才说 | 又两批 50 连测：**48 次、49 次全对**；三批合计 **144/150 = 96%**，150 次里只有一种错：多出一张带“页面上没有的单号”的行 |
| 同上 + 截点按页面空白带（Step 161） | 16 单那张图（最后一单 10 行 / 20.00）：**4 连测都是 16 张、最后一单每次都是 10 行 20.00**（改之前 1~2 行）；23 单那张图仍 23 张 |

## 3. 合并：同一块被读了两次怎么办

`mergeOrders` 的输入是"每段的答案"，输出是整页的订单。要点：

1. **同一个订单号 = 同一单**：行拼接，缺失字段互补；号长按整页众数校正（读多/读少一位时）。
2. **两个对象都是同一块**（模型把一块答成两条）：
   - 实付**相同** → 并回一张（一页只印一个实付款）；
   - 其中一条**完全没有金额**（`paidTotal=0.00`、店铺空）→ 视为同一块的片段；
   - 一条的金额恰是另一条 **单价 × 数量** → 小的那条是单价，丢掉。
3. **两条不同块被读成同一个号**：实付**不同**时才拆开留着（宁可多一行让人删，也不吞单）。
4. 跨段：同号且同实付 → 合并；同号不同实付 → 拆开。
5. **拆开之后还能折回去**：拆开是因为“一块只印一个号”，但如果**图上的块数比读出的单数少**，
   那这个拆就是错的。`foldExtraReads(orders, blocks)` 把单号相同、金额最接近的一对先合回一张，
   明细取并集（`rowIdentity` 去重），实付取“和明细合计更接近”的那份，然后照常跑金额核对。
   **只认同一个单号**：少一位的号（`numbersOfTheSameOrder`）属于另一个问题，拿它来合会吞掉真单。
   实测：20 次里有 3 次会抛出“单号相同的两行”，其中能被折回去的都变成了 23 张（日志
   `The reads of one order number were folded: 24 -> 23`）。
6. **单号的第二遍读**：`noteTheSecondRead` 把“只读单号那一条带子”的结果记下来（`headerOrderNo`，
   顺便补空着的日期 / 店铺），合并后 `settleNumbers` 用**这一页印单号的位数**（众数，样本 ≥3）判：
   位数对得上的那次赢；两次等长就**保留第一次**，并把两次都写进 note。
   **别改回“放大那次为准”**：50 连测里出错的那 3 次，恰恰是带子读错、整页读对。

相关规则函数：`OirOrders.mergeOrders / numbersOfTheSameOrder / onePrintsThePriceOfTheOther`…（都在本包 `OirOrders` 里，不再跨包）。

## 4. 整理：让每一单的"明细合计 = 实付 + 优惠 − 运费"

`OirOrders.tidyOrder` 依次尝试（只用**能对上钱**的那种读法）：

| 场景 | 规则 |
| --- | --- |
| **模型给的是单价，不是行金额** | `readingThatAddsUp` 的第二遍读法把金额 × 数量，容许 `0.005 × 件数`：六行 210 件合计 12.21 → 2564.10（实付 2562.84，差 1.26 是 2.124 印成 2.13） |
| 一包单价被当成整行金额 | `moneyOfOnePack`：缺口正好是某行金额 ×(包数−1) 时，那一行改成 `单价 × 包数`（要求恰好一行能解释） |
| 把"实付款"当成一行明细 | `withoutTheRowThatIsThePaidTotal`：≥3 行且只有一行等于整单实付时删掉它 |
| 单价被当成行金额 | `readingThatAddsUp`：允许 ×数量 |
| 重叠段读到的重复行 | `withoutRepeatedRows`：只在明细合计大于实付时删，删到对得上为止 |
| 页面底部"猜你喜欢"被算进最后一单 | `withoutTheTailThatDoesNotFit` |
| 实付含运费被算两遍 | `goodsWithoutFreight` |
| 整块只有一行 | 该行金额 = 实付 − 运费 |
| **没读到优惠（模型答 `"discount":"0"`）** | `checkOrderTotals` 按 `实付 = 货款 + 运费 − 优惠` 自己算出差额写进 `discount`，**不再报红**。三个上限：差额 ≤ 货款一半（`MAX_DISCOUNT_SHARE`）、≤ 最贵那一行的金额（`dearestRow`）、回答里不许有缺行（`rowsMissing`）。少了任何一个，一块被答五遍（975.00 vs 实付 195.65）就会被当成 780.35 元的优惠入库（Step 162） |
| **一行没有料号**（标题就是名称） | `parseOrderArticleLines` 收 `\t名称\t数量\t金额` 这种**三格**行（料号由 `codeFromName` 造），也收四格里首列为空的。OFBiz 会把请求参数 `trim()`，所以空首列到了服务里已经是三格（Step 163） |

金额核对容差 `roundingSlack = max(Σ min(0.005 × 件数, 0.10) + 0.005, 货款 × 0.5%)`（页面把单价四舍五入到分）。
前半句是“一行最多一毛”，后半句是“整块最多差千分之五”：单价舍入是**占比很小**的误差（2562.84 读成 2564.10），
漏读/读错一行是**占比很大**的误差（15.90 读成 11.40），所以两者靠占比就能分开。
常量名 `HALF_A_FEN` / `MAX_ROW_SLACK` / `RELATIVE_SLACK`，两份读数之间的容差是 `MONEY_TOLERANCE = 0.06`（六分），
都带来源说明放在 `OirOrders` 顶部。

## 5. 已知失败模式（都是实测到的，不是猜想）

| 现象 | 现在的处理 |
| --- | --- |
| 模型整块漏读（21 张） | 段切小后基本消失；整页仍少时页面会提示"截图上看上去有 N 张，这次只读出 M 张" |
| **模型凭空多编一张单（+1 行）** | 不再“无法发现”：图上的按钮数是一份不依赖模型的第二意见（`blockCountOf`），读出的单数与它差 1~2 时页面会点出来（Step 153）。**不自动删**——删哪一行只有人知道 |
| 19 位订单号少一位 / 相邻两位写反 | 用"整页号长众数 + 同实付 + 一条子序列"规则并回；仍可能读错，属已知局限 |
| 一块印 4 行、模型只读出 2 行 | `rowCount` 与行数比对后提示"截图印了 4 行明细，这次只读出 2 行" |
| 一块印十几行、模型只读出 5 行（两行字一样，钱差 5.10） | 切段的钱现在也查（`moneyCanBeChecked`：这一段打印 N 块完整、正好答了 N 单，说明没有半块）；第二次问会把**丢的钱**说出来（`OirOrders.moneyGapOf`：只读出 10.80，实付 15.90，还差 5.10 元），并且这条原因**只再问一次**。**只查“段里全是整块”的那种段**：试过连夹着半块的段一起查（豁免最外两张），同一张 14 单的图反而更差 |
| **最后一单只读出 1~2 行，钱却是对的** | 截断把它切掉了：一行 `¥2.00 x1` 相同的商品，模型照着实付 20.00 就能“补”出 10 行。现在截点落在页面的空白带上（`tailCutOf`），并且永远不早于旧的“一个块”截法；实在找不到宽空白时仍可能切掉最后一块，靠页面的“请核对”提示兜 |
| 模型为了让合计对上改动某一行（`446.04` = 210 件的 2.124） | 提示词写明"不要为了让合计对上改动某一行、也不要把实付款写成一行"；这类错误钱是平的，只能靠人核对 |

## 6. 请审计的问题（欢迎直接改）

1. **块边界检测**：现在靠"橙色按钮 + 最宽缝"。有没有更稳的信号（页面分隔线、图片色块的周期、频域峰值）？
   **实测过了（2026-10-27，3434×16384、23 单的真实页）**：
   - 旧规则（一行里橙色总量 ≥ 宽度的 4%）得到 **32** 个锚点：23 个是真正的「再买一单」按钮，另 9 个是
     橙色**文字行**——表头的 `订单详情 >` / `交易成功` 一行就能凑出 200 px 橙色，券条同理；
   - 换成「**最长一段连续橙色** ≥ 宽度的 4%」后是 **25** 个：23 个块按钮 + 页头那个按钮（y≈118，x≈2533）
     + 页面底部推荐区的按钮（y≈13276，x≈1666）。块按钮彼此 x≈2431~2448、带宽 187~204 px，与那两个明显不同。
   - 所以「数按钮」**只差去掉页头/页尾两个**（它们的 x 与其它 23 个差 > 60 px）。
   - 这件事**后来做完了**（Step 153）：`blockCountOf` 把锚点按“按钮左边缘落在哪个采样点”分组，
     **取最多的一组**（相邻采样点算同一组，因为两种按钮样式会差一个采样点）。真实页得到 **23**：
     组 143+144 = 4+19，页头（149）和页尾（97/98）各自成组、只有 1~2 个。
     **退款 / 交易关闭的单也印按钮**（用户确认：可能印「再买一单」或「加入购物车」），所以不会少算；
     但为了不误报，只在**与读出的单数相差 ≤ 2** 时才提示（差很多说明数到的是推荐区的按钮），
     而且**只提示不删行**。实测同一张图 10 连测：9 次 23/23 无提示；有 1 次模型只读出 21 张，
     消息里自动多出“图上有 23 个「再买一单」，这次只读出 21 张单，可能漏了 2 张”——这正是以前看不见的那种丢单。
   - 「最长连续橙色」这一条**已经改进代码**（`blockAnchors`），切点也随之变了（12 段不变，个别切点移动
     几百行），同一张图 10 连测仍是 **10/10 都是 23 张 / 23 个不重复号**，与改之前持平。
     量这个的工具放在 `tools/oir-anchors/`（`AnchorAudit` 打印锚点与切点，`LongestOrange` 打印每段的带宽）。
   - **清单要排序**（Step 158，真 bug）：`listButtons` 是按“左边缘落在哪个采样点”的组拼出来的，
     两种按钮样式差 2 像素就落进两个组，拼出来的顺序**不是从上到下**，而 `blocksInside` 是按相邻两个按钮
     配对的——一张 14 单的页面上它把“这一段有几块完整”数成了 5（那一段 2068 行、按块高 689 最多 3 块）。
     现在返回前 `Collections.sort`。
2. **段高估计**：自相关取全局最大值。是否该用"多个候选峰值 × 段内块数一致性"来选？换平台/换缩放是否稳？
3. **合并规则**：现在是一串 if。能否换成一个**全局最优化**（把每段读法当作候选块，用费用函数做序列对齐 /
   匈牙利匹配），从而一次处理"漏读、重读、串号、串行"？
4. **多次采样 + 投票**：同一段读 2~3 次，按"单号 + 实付 + 明细"投票，是否比现在"重试 + 打分保留最好"更稳？
5. **提示词**：能不能换成更"窄"的输出格式（例如每单一行、字段用固定分隔符），让模型少犯格式错误？
6. **金额核对**：淘宝 / 天猫里还有哪些写法（满减、店铺券、跨店优惠、"实付含运费"）没覆盖？

## 8. 约束（改的时候别破坏）

- **不能写库**：这个包只返回订单列表；入库、幂等（订单号为键）、退款黑名单都在调用方。
- **返回结构不能变**：`{"ok","message","count","orders":[{...}]}`，页面的核对表按它渲染。
- **`MfgOrderScan` 这个类名不能删**：`controller.xml` 的 `<request-map uri="orderImage">` 指向它。
- 判定阈值（容差、包数上限、段高上下限）都在类顶部，改了请同步本文件 §2 §4 的说明与 `AGENTS.md`。

## 9. 外部审计意见的处理（2026-10-27）

第三方按「代码结构 / 算法稳健性 / 性能 / 可测试性 / 细节」提了十五条，结论如下。

**已改（行为不变，161 个单测 + 真实图片 23 张 / 12 段重跑一致）**

| 意见 | 做法 |
| --- | --- |
| 魔法数字散落 | `OirOrders` 顶部集中为 `MONEY_TOLERANCE` / `HALF_A_FEN` / `PRACTICALLY_ZERO` / `MAX_PACKS` / `MISSING_DIGITS_ALLOWED`，注释写明来源与实测依据 |
| 正则每次重编译 | `TRADE_NOTE` / `PACK_SUFFIX` / `BLANKS` 改成 `static final Pattern`（`bareCode` / `rowKey` 用） |
| `anonymousOk` 含义模糊 | 参数改名 `partial`，与 `OirScan` 里那个切片标志同名 |
| 线程池未优雅关闭 | `shutdownNow()` + `awaitTermination(5s)` 放进 `finally`（超时的切片会被取消，不留线程和图片） |
| 重试固定间隔 | `pause(attempt)` 指数退避 700 / 1400 / 2800 ms |
| 日志不够详细 | 每次重发记 `Attempt N of M scored X (kept Y, best Z), asking again: <原因>`，原因由 `whyAskAgain()` 给出 |
| 悬空 javadoc | `orderListFrom(String)` 上面那段（`nameWithFullCode` 的）是搬迁留下的，已换成正确说明 |

**没改（附理由，欢迎再挑战）**

| 意见 | 为什么不改 |
| --- | --- |
| 容差收紧成 `max(0.01×件数, 0.05)` | `0.005×件数` 不是拍脑袋：页面把单价印到分，100 件 × 单价误差 0.005 = 0.5 元。收紧会让 Step 129 修掉的「请核对」噪声回来（27 张单从 7 条降到 0 条），那些差额都是页面四舍五入，不是漏读 |
| 金额换 `BigDecimal` | 钱只在 `round2(...)`（两位）之后比较，误差来自**页面四舍五入**而不是二进制浮点；换 BigDecimal 要改每一处规则，且不改任何一次判定结果 |
| `refunded` / `closed` 改枚举 | 这两个字段是给页面、`ordersJson`、`MfgRefundedOrder` 的**线格式**（字符串），枚举只会在边界反复转换 |
| 块高多信号融合 | 切点是靠按钮缝定的（§2），块高只决定「一段放几块」；实测 12 段、10 连测 23/23，动它是拿已验证的结果赌未验证的收益。审计问题 2 仍然开放 |
| `VisionClient` 接口注入 | `askVision` 已 `public static` 且只做一次 HTTP；端到端已有 `mock-vision.ps1` 假接口。抽接口会把静态工具类改成需要注入状态的对象 |
| `tidyOrder` 拆小方法 | 这十几步的**顺序本身就是规则**（Step 129：`goodsWithoutFreight` 必须在丢汇总行之前）。拆进独立方法会让这个约束藏起来，而它正是出过错的地方；每步已有注释 |
| 切片先 PNG 再 JPEG | 切片的大小主要来自商品图，PNG 重压收益很小；JPEG 只在 >4 MB 时走，实物小字实测可读 |
